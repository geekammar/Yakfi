# FlowPilot — Vercel Deployment Guide

> Step-by-step: from this repository to a live, shareable FlowPilot URL.
> **In a hurry? Section 0 (Quick Deploy) gets there in under 5 minutes.**
> Companion reference: `ENVIRONMENT_VARIABLES.md`.
> Requirements: a [Neon](https://neon.tech) PostgreSQL database and (for the
> GitHub-connected flow) the repo pushed to GitHub (`pnpm release` handles that).
>
> **Execution boundary:** run deployment, build, database and CLI commands in
> Vercel, existing CI, or an authorized isolated cloud runner — never on the
> VPS. On the VPS, use source/text inspection, editing and Git only.

## TL;DR

1. Neon database exists + schema applied (`pnpm db:deploy` from desktop).
2. Push repo to GitHub (private).
3. Vercel → Import the repo → add the 4 environment variables → Deploy.
4. Open `https://<your-app>.vercel.app/api/health` →
   `{"status":"ok","deploymentReady":true,…}`.
5. Sign in with the demo credentials (after `pnpm db:seed` on the demo DB, or
   set `DEMO_MODE=true` so deploys seed automatically).

CLI alternative to steps 2–3 (single command, gates first):

```bash
pnpm deploy        # env + DB + Prisma + auth + build gates → production URL
```

## SECTION 0 — Quick Deploy (< 5 minutes)

> Merged from the former quick-deploy one-pager (PROMPT-13.5 reset).

**Prerequisites (once, ~2 min):** a free [Neon](https://neon.tech) PostgreSQL
project (copy the connection string from Project → Connect, keep
`?sslmode=require`) · a free [Vercel](https://vercel.com) account · Node ≥ 20

- pnpm (or run `bash scripts/bootstrap.sh` — Windows `bootstrap.ps1`,
  Android `bootstrap-termux.sh`).

```bash
pnpm install && pnpm run setup     # deps + .env.local (random auth secret)
# ↓ edit .env.local (see table), then:
pnpm deploy                        # gates → deploy → prints the URL
```

`.env.local` values (the deploy gate validates all of them):

| Variable              | Value                                            |
| --------------------- | ------------------------------------------------ |
| `DATABASE_URL`        | `postgresql://…@…neon.tech/db?sslmode=require`   |
| `BETTER_AUTH_SECRET`  | already generated by `pnpm run setup`            |
| `BETTER_AUTH_URL`     | `https://<your-app>.vercel.app` (see note below) |
| `NEXT_PUBLIC_APP_URL` | same as `BETTER_AUTH_URL`                        |
| `DEMO_MODE` _(opt.)_  | `"true"` → demo data seeded before every deploy  |

> **First deploy chicken-and-egg:** the URL is only known after deploying.
> Easiest fix: pick the project name first (Vercel names the app for you if
> you `vercel link` / import with that name — URL = `https://<name>.vercel.app`)
> and set the two URL variables to it **before** deploying. Alternatively
> deploy once, then set the URLs in Vercel → Settings → Environment Variables
> (Production **and** Preview) and redeploy.

First-time Vercel CLI setup (CLI path only):

```bash
pnpm dlx vercel@latest login     # browser login (once per machine)
pnpm dlx vercel@latest link      # connect this folder to the project
```

(Or skip the CLI: push the repo to GitHub — `pnpm release` — and import it in
Vercel; every push to `main` then redeploys automatically.)

**Verify (30 seconds):** `/api/health` →
`{"status":"ok","deploymentReady":true,"database":"connected",…}` · sign in
at `/sign-in` with `admin@flowpilot.app` / `Admin@1234` (with
`DEMO_MODE=true`, or after `pnpm db:seed` + `pnpm db:deploy` for the schema)
· share the URL — demo package: `CLIENT_DEMO.md`.

| Command               | What it does                                                  |
| --------------------- | ------------------------------------------------------------- |
| `pnpm deploy:check`   | Readiness gate only → READY / NOT READY with fixes            |
| `pnpm deploy`         | Gate → **production** deploy → URL (share this one)           |
| `pnpm deploy:preview` | Gate → preview deploy → URL (internal use; auth may not work) |

Stuck? `TROUBLESHOOTING.md` + Section 6 below.

## SECTION 1 — Create Vercel Project

1. Sign up / log in at [vercel.com](https://vercel.com) (free Hobby plan is
   enough for pilots; the team's Pro plan works identically).
2. Click **Add New… → Project**.
3. Do **not** continue past the import screen yet — the repository must be on
   GitHub first (Section 2). If you prefer deploying straight from this
   machine without GitHub, see **CLI path** at the end of Section 2.
4. When prompted, **do not** create a database through Vercel's marketplace
   wizard — FlowPilot uses its own Neon project (Architecture: Vercel + Neon).

What Vercel auto-detects from the repo (no action needed):

| Setting         | Detected value                                        |
| --------------- | ----------------------------------------------------- |
| Framework       | Next.js (16, App Router)                              |
| Package manager | pnpm (`packageManager` field + `pnpm-lock.yaml`)      |
| Build command   | `pnpm db:generate && pnpm build` (from `vercel.json`) |
| Node.js         | default (satisfies `engines.node >= 20.9.0`)          |

## SECTION 2 — Connect GitHub Repository

1. Push the repository to GitHub if not done yet:

   ```bash
   gh auth login          # once per machine
   pnpm release           # gated: creates private repo flowpilot + pushes main
   ```

   (Manual equivalent: `docs/RELEASE_PROCESS.md`.)

2. Back in Vercel **Add New… → Project**, find the private `flowpilot` repo
   (grant Vercel access to private repos when asked) and press **Import**.
3. Pick a project name — it becomes the URL: `<name>.vercel.app`
   (e.g. `flowpilot-demo` → `https://flowpilot-demo.vercel.app`).
4. Leave the Framework/Build settings as auto-detected (they come from
   `vercel.json`).

**CLI path (no GitHub needed):** deploy directly from this machine instead —

```bash
pnpm deploy:check             # full readiness gate: env + database + Prisma + auth + demo + build
pnpm dlx vercel@latest login  # once per machine
pnpm dlx vercel@latest link   # once per project (follow prompts)
pnpm deploy                   # production deployment (same full gate, then deploy → URL)
pnpm deploy:preview           # preview deployment (auth may not work on preview URLs)
```

Every push to `main` (GitHub flow) then redeploys automatically — that is the
"easy to redeploy" loop: full `pnpm verify` in existing CI or an authorized
isolated cloud runner → commit → push → Vercel builds. Do not run package
commands on the VPS.

## SECTION 3 — Configure Environment Variables

**This must be done BEFORE the first deploy** — the build fails fast
(Arabic Zod error) if any variable is missing.

In Vercel: **Project → Settings → Environment Variables**, add each of the
four (see `ENVIRONMENT_VARIABLES.md` for exact formats and generation):

| Name                  | Example value                     | Environments        |
| --------------------- | --------------------------------- | ------------------- |
| `DATABASE_URL`        | `postgresql://…​?sslmode=require` | Production, Preview |
| `BETTER_AUTH_SECRET`  | 64-char random string             | Production, Preview |
| `BETTER_AUTH_URL`     | `https://<your-app>.vercel.app`   | Production, Preview |
| `NEXT_PUBLIC_APP_URL` | `https://<your-app>.vercel.app`   | Production, Preview |

Rules that bite:

- Generate the secret once and reuse it everywhere (`node -e "console.log(require('node:crypto').randomBytes(48).toString('base64'))"`).
  A different secret per environment invalidates sessions of the other one.
- `BETTER_AUTH_URL` and `NEXT_PUBLIC_APP_URL` must match the **production**
  domain. `NEXT_PUBLIC_APP_URL` is baked in at build time.
- Preview deployments share these values → test auth flows on the production
  domain (preview hosts are not in `trustedOrigins`).
- Apply the database schema **before** the first successful deploy:

  ```bash
  pnpm db:deploy     # prisma migrate deploy — run from desktop (not Termux)
  ```

Sanity-check in an authorized non-VPS environment or CI first — the same validation the deploy gate runs:

```bash
pnpm vercel:check
```

## SECTION 4 — Deploy

1. In the Vercel import screen (Section 2) press **Deploy** — or, for an
   existing project, **Deployments → … → Redeploy**, or just push to `main`.
2. First build takes ~2–4 minutes. The build runs
   `pnpm db:generate && pnpm build` (Prisma client is gitignored and must be
   regenerated on every build — handled automatically).
3. If the build fails, the error is shown inline — see Section 6.

Local alternative with the same guarantees (readiness gate first, explains
failures, returns the deployment URL):

```bash
pnpm deploy:check       # env + database + Prisma + auth + demo + build → READY / NOT READY
pnpm deploy:preview     # full gate → preview deployment URL
pnpm deploy             # full gate → production deployment URL (deploy:production = alias)
```

> **Production is CLI-linked — pushes do not deploy it.** `flowpilot-prod`
> (linked in `.vercel/project.json`) has **no Vercel Git connection**, so
> `pnpm ship` / `git push` update GitHub only. Promote production after every
> ship with `pnpm deploy:production`, then confirm `/api/health` reports the
> new `package.json` version. Only Git-connected projects redeploy
> automatically on push (this repo also has a legacy `flowpilot_v3`
> connection — it is not the production URL).

## SECTION 5 — Validate Deployment

1. **Liveness & readiness** — open `https://<your-app>.vercel.app/api/health`:

   ```json
   {
     "status": "ok",
     "version": "0.29.1",
     "environment": "production",
     "timestamp": "2026-08-29T…Z",
     "deploymentReady": true,
     "database": "connected",
     "missingEnvVars": []
   }
   ```

   `deploymentReady: false` with `database: "unreachable"` → wake/check the
   Neon project before demoing (idle-suspended databases are the usual cause).

2. **Database** — sign in at `/sign-in` (needs seeded demo users on the DB:
   `pnpm db:seed` from an authorized non-VPS environment). If login works, Better Auth ↔ Neon are wired.
3. **PWA** — on Android Chrome: install prompt appears, home-screen icon is
   the FlowPilot mark, offline page shows in airplane mode.
4. **RTL/Arabic** — pages render `dir="rtl"`, Arabic copy, IBM Plex Sans Arabic.
5. **Redeploy loop** — make a change → full `pnpm verify` in CI → commit →
   push → Vercel rebuilds → `/api/health` shows the new version after you bump
   `version` in `package.json`.

| Symptom                                                             | Fix                                                                                                                                                                                                   |

| Build succeeds, every page errors at runtime (`P1001` / connection) | `DATABASE_URL` unreachable from Vercel: check Neon project is alive (idle-suspended — wake in console), the string ends with `?sslmode=require`, and Neon's network access allows Vercel.             |
| Login/redirect loops or 403 on auth routes                          | `BETTER_AUTH_URL` ≠ actual domain. Set it to the exact production URL (https, no trailing slash) and redeploy.                                                                                        |
| Auth works on production but not on `*.vercel.app` preview URLs     | Expected — previews aren't in `trustedOrigins`. Test auth on the production domain.                                                                                                                   |
| `/api/health` returns old version after a release                   | Bump `version` in `package.json` (health reports it verbatim) and redeploy.                                                                                                                           |
| `/api/health` says `"deploymentReady": false`                       | Read `database` / `missingEnvVars` in the same response: unreachable DB → wake the Neon project (idle suspend) and check `?sslmode=require`; missing vars → add them in Vercel settings and redeploy. |
| Installed PWA shows old UI after a deploy                           | The service worker updates on next visit (network-first navigations). Hard-refresh once or bump `VERSION` in `public/sw.js`.                                                                          |

### 7.3 Liveness vs Readiness & Neon Suspension Impact

- **`GET /api/health/live` (Lightweight Liveness — HTTP 200, zero DB queries):**
  wired to Render's `healthCheckPath`. Render probes `healthCheckPath` roughly
  every 5 seconds; pointing that continuous probe at a DB-backed route would
  issue ~17,280 `SELECT 1` queries/day, **preventing Neon scale-to-zero idle
  suspension** and burning ~730 compute-hours/month continuously.
- **`GET /api/health` (Explicit Deployment & DB Readiness — HTTP 200 vs 503):**
  checks `REQUIRED_ENV_VARS` and executes a bounded 3s Prisma `SELECT 1`.
  Returns **HTTP 200** (`status: "ok"`, `deploymentReady: true`) only when all
  required variables are present and `database === "connected"`; returns **HTTP
  503** (`status: "degraded"`, `deploymentReady: false`) otherwise. Used by
  operator cutover checks and `.github/workflows/production-release.yml`.
- **Runtime commit identity:** both health routes and
  `/api/operator/cutover-readiness` read `RENDER_GIT_COMMIT` (falling back to
  `VERCEL_GIT_COMMIT_SHA`), reporting the exact 40-character deployed commit.

### 7.4 Platform-Neutral Headers & Telegram `after()` Semantics

- **`/sw.js` and `/offline.html` headers:**
  `Cache-Control: public, max-age=0, must-revalidate` now lives in
  `next.config.ts` (`headers()`), enforced identically on Render, local Node,
  and Vercel.
- **Telegram `next/server` `after()`:** retained in
  `src/app/api/telegram/webhook/route.ts`. On Render's persistent Node process,
  `POST /api/telegram/webhook` authenticates the secret token and flushes HTTP
  `200` promptly while `after()` runs the Conversation Engine + outbound
  `sendMessage` on the Node event loop.
- **Crash / OOM / redeploy limitation:** once HTTP `200` is flushed, Telegram
  marks the update delivered and will **not** retry if the Node process crashes
  (e.g., 512 MB OOM) or receives `SIGKILL` mid-turn during a redeploy. Avoid
  triggering redeploys while active customer turns are mid-flight, and inspect
  conversation/turn logs after any restart.

     `scripts/render-telegram-cutover.ts` expose `operation=preflight` (default,
     read-only), `operation=apply` (explicit), and `operation=reconcile`
     (explicit guarded secret reset). The destination is pinned to
     `https://yakfi.onrender.com/api/telegram/webhook`; fixed
     workspace/service, Business/Connection/Bot, selected active DB, exact
     checkout/deployed SHA, and expected version are required. Preflight
     resolves the selected bot credential from the selected DB/master key,
     verifies `getMe`, calls `getWebhookInfo` (URL, pending count, observation
     time, observed vs desired allowed_updates, last error), and verifies the
     signed Render `/api/operator/cutover-readiness` proof. Apply requires a
     fresh preflight, `pending_update_count === 0`, the expected current URL,
     exact `allowed_updates: ["message", "callback_query"]`, never enables
     `drop_pending_updates`, and treats a genuinely exact already-at-destination
     registration as a zero-write no-op. A matching URL with extra/missing
     allowed_updates is blocked as `ALREADY_AT_DESTINATION_SETTINGS_MISMATCH`,
     not treated as exact readiness. When exact `allowedUpdates` is supplied,
     post-apply verification checks the Telegram-observed set exactly and
     rejects extra/missing/malformed sets. Unknown/non-zero backlog or any
     failed identity/readiness check blocks apply. Do **not** use the legacy
     `cutover-main-runtime-*` Vercel operations for Render. The workflow must
     exist on `main` before its first manual dispatch; GitHub rejects dispatch
     from a feature branch.
   - **Explicit reconciliation (`operation=reconcile`):** requires a fresh
     preflight, Render current URL, zero backlog, resolved identity and signed
     runtime readiness, then resets the Telegram webhook secret in place and
     persists the new DB hash with exact allowed_updates. It is never automatic
     after an uncertain failure. `getWebhookInfo` cannot reveal the webhook
     secret; a stored hash alone does not prove it matches Telegram; signed
     readiness proves bot credential resolution, not webhook secret
     synchronization. A real delivery test is still required for delivery
     acceptance.
   - **Partial-failure boundary:** Telegram `setWebhook` and PostgreSQL
     `webhook_secret_hash` persistence are not atomic. On partial or ambiguous
     failure, inspect `getWebhookInfo` and the DB hash, then use the reviewed
     reconciliation procedure; never retry blindly.
6. **Post-Cutover Verification & Release Tagging:**
   - Re-verify `getWebhookInfo` (`url === https://<render-origin>/api/telegram/webhook`,
     `allowed_updates` includes `message` and `callback_query`).
   - Run `.github/workflows/production-release.yml` with `publish_release=true`
     only after the exact SHA is verified live on Render.
